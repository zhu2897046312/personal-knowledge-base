# 前端性能优化

这次优化下来，我的感觉是：不要一上来就想着拆包。先看首屏到底在等什么，很多时候真正拖慢页面的不是某一个神秘的大 JS，而是首屏加载了太多暂时用不到的东西。

## 这次优化的结论

这次 LCP 从 9s 左右降到 3s 多，提升最大的一步不是拆包，而是把首屏外的数据和图片延后加载。

我的理解是：

1. 首屏只保留必须马上出现的内容，比如 header/nav 和 hero。
2. 文章列表、分类、推荐文章、非首屏图片，这些都可以懒加载。
3. 图片不能只看格式，还要看移动端实际加载了多大的图。
4. 最后才考虑 JS 拆包和 hydration，不要一开始就把问题复杂化。

## 1. 先看首屏，能懒加载的先懒加载

第一步先判断哪些东西是首屏必须要的。

像首页这种页面，首屏真正需要的是：

- 顶部导航
- hero 文案
- hero 图片

其他内容，比如文章列表、分类、推荐文章、底部区域，其实不需要阻塞首屏。尤其是这些内容还要发 API 请求时，更应该考虑懒加载。

这一步对性能提升最大。因为它减少的不只是网络请求，也减少了 SSR 等待、客户端 hydration 和首屏 JS 执行压力。

我的经验是：  
只要用户第一眼看不到，就先不要让它影响第一屏。

## 2. 图片格式和移动端尺寸要单独处理

图片优化不能只做“转 WebP”这么简单。

这次做了几件事：

- 上传图片统一转成 WebP。
- 首屏图额外生成 AVIF/WebP 多个尺寸。
- 使用 `picture + srcset + sizes` 让浏览器按设备选择图片。
- 移动端限制图片最大候选，比如不要让移动端直接选 1024 的图。
- 非首屏图片加 `loading="lazy"`。
- 非关键图片降低优先级。

这里有个容易忽略的问题：移动端 Lighthouse 往往是高 DPR。比如页面上图片显示 334px，但 DPR 是 3 时，浏览器可能会觉得 1024 图最合适。所以移动端 source 里最好不要无脑放桌面大图。

我现在的理解是：  
移动端图片要单独控制，不能只是复用桌面端资源。比如把 1024 限到 720/768，很多时候肉眼差别不大，但 LCP 会明显好很多。

## 3. 最后再考虑 JS 和拆包

拆包不是第一步。

Nuxt/Vite 本身会做基础拆包，如果一开始就手动拆，很容易把问题搞复杂，而且不一定能解决真正的瓶颈。

只有当图片、首屏 API、懒加载都处理完以后，TBT 还是很高，再考虑：

- 首屏是不是用了太多 Nuxt UI 组件。
- 全局组件是不是过早 hydration。
- 登录态、主题切换、语言切换这种交互能不能延后。
- admin/member 这种后台重组件有没有进入公共首页路径。
- 是否需要把非首屏组件改成 client-only 或延迟加载。

我的顺序是：  
先减少首屏要做的事，再减少首屏要加载的资源，最后才考虑怎么拆 JS。

## 我的排查顺序

以后可以按这个顺序来：

1. 先跑 Lighthouse，看是 LCP、SI、TBT 还是 CLS 差。
2. 如果 LCP 差，优先看首屏图片、首屏 API、字体、SSR 等待。
3. 如果 SI 差，看是否有非首屏内容提前加载。
4. 如果 TBT 差，看首屏 JS 执行和 hydration。
5. 如果 CLS 差，看图片宽高、容器尺寸、动态内容占位。

这次最明显的经验是：  
性能优化不要只盯着文件大小。文件小了不代表页面快，关键是首屏到底加载了什么、执行了什么、等了什么。
