# 目标

梳理多轮对话场景下 RAG 容易被忽略的一步——**Query Rewriting（提问改写）**：像"那它多少钱"这种指代性追问，直接拿去 Embedding 检索大概率不准，需要先用 LLM 结合历史把追问改写成独立问题，再做向量检索。同时记录改写带来的 Token 成本该如何工程化压低。

# 知识点

## 标准多轮 RAG 架构：两次 LLM 调用 + 一次向量检索

```text
用户输入 ("那它多少钱？") + 历史对话
        │
        ▼
[ 步骤 1: LLM 改写 Query ]  ──► 生成独立问题 ("PKB Server 的价格是多少？")
        │
        ▼
[ 步骤 2: Embedding + 向量检索 ] ──► 召回相关文档 Chunk
        │
        ▼
[ 步骤 3: 组装 Prompt ] (系统指令 + 召回 Chunk + 历史记录 + 当前提问)
        │
        ▼
[ 步骤 4: LLM 生成最终回答 ]  ──► 输出给用户
```

### 1. 提问改写（Query Rewriting）

- 输入：最近 N 轮历史对话 + 当前用户提问
- LLM 任务：指代消解（Coreference Resolution），消除"它""这个"等模糊词，补齐缺省的主语/谓语
- 输出：一个不依赖任何上下文就能被看懂的**独立问题（Standalone Query）**

### 2. 向量检索

只用改写出的独立问题去 Embedding + 检索，**千万不要拿原句或全部历史对话去 Embedding**，否则向量噪点极多。

### 3. Prompt 组装与最终回答

输入 = 系统 Prompt + 检索出的知识库 Chunk + 历史对话记录（保证连贯性）+ 用户原始/改写后提问。

## 落地工程优化点

1. **改写阶段选用轻量小模型**：改写只是语义补全，不需要强推理能力，用响应最快的轻量模型（DeepSeek-V3、小参数本地模型），回答阶段才用大模型。
2. **首轮/完整提问的跳过机制（Skip Logic）**：第一轮对话无历史，直接跳过改写；提问本身完整（有明确主谓宾、无指代词）也可跳过。
3. **改写专用 Prompt**：只输出改写后的单行问题，不回答、不展开。

## 为什么改写的 Token 成本划算：5 个工程手段

不改写直接检索会导致召回准确率骤降，第二次 LLM 也会 Garbage in, Garbage out，等于白白浪费。可以把改写 Token 成本降低 70%~90%：

1. **利用 Context Caching（前缀缓存）**：System Prompt 和 History 重复度高时，命中缓存的输入 Token 费用通常只有原价的 1/10 甚至更低。
2. **改写历史只传滑动窗口**：只截取最近 1~2 轮（最多 3~4 条消息），因为口语指代 90% 以上指向上一轮提到的名词，输入可控制在 200~300 Tokens。
3. **严格限制改写步骤的 `max_tokens`**：直接限制在 50~100，输出消耗极微量。
4. **条件触发跳过机制**：首轮跳过；提问长度 >15 字且无指代词、包含明确名词时也跳过。
5. **模型分级**：改写用便宜/极速小模型（甚至本地 1.5B/7B），生成回答才交给能力最强的主模型。

# 示例

假设用 DeepSeek-V3：改写步骤精简上下文（~200 Token）+ 极短输出（~20 Token），单次成本毫厘级，换来的是向量检索命中率从 30% 提升到 90%+。

# 总结

> 多轮 RAG 的关键流水线是"先用 LLM 处理提问历史 → 改写成独立问题 → 回 Embedding 检索 → 最后组装 Prompt 提问 LLM"。改写增加的 Token 成本可以通过前缀缓存、滑动窗口、max_tokens 限制、跳过机制、模型分级五个手段压到很低，用极小的改写开销换取稳定的召回率是目前性价比最高的解法。
