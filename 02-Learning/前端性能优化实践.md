# 目标

按正确顺序做前端性能优化：先看首屏在等什么，最后才考虑 JS 拆包。

# 知识点

这次 LCP 从约 9s 降到 3s 多，提升最大的不是拆包，而是**首屏外数据与图片延后加载**。

原则：

1. 首屏只保留必须马上出现的内容（如 header/nav、hero）
2. 文章列表、分类、推荐、非首屏图片可懒加载
3. 图片既要看格式，也要看移动端实际候选尺寸
4. 最后才考虑 JS 拆包与 hydration

## 1. 先看首屏，能懒加载的先懒加载

首页首屏通常只要：顶部导航、hero 文案、hero 图片。其余阻塞首屏的 API / 区块应延后——减少的不只是网络，还有 SSR 等待、hydration 与首屏 JS。

经验：用户第一眼看不到的，就先不要影响第一屏。

## 2. 图片格式和移动端尺寸要单独处理

- 上传统一转 WebP；首屏可再出 AVIF/WebP 多尺寸
- `picture + srcset + sizes` 按设备选择
- 移动端限制最大候选（勿直接选 1024）
- 非首屏 `loading="lazy"`，非关键降低优先级

注意：移动端 Lighthouse 常为高 DPR；显示 334px、DPR=3 时浏览器可能选 1024。移动端 source 不要无脑放桌面大图；把 1024 限到 720/768 往往肉眼差不大、LCP 更好。

## 3. 最后再考虑 JS 和拆包

Nuxt/Vite 已有基础拆包。先处理图片、首屏 API、懒加载后，若 TBT 仍高，再看：

- 首屏是否用了过多 Nuxt UI
- 全局组件是否过早 hydration
- 登录态/主题/语言能否延后
- admin/member 是否进了公共首页路径
- 非首屏是否 client-only / 延迟加载

顺序：先减少首屏要做的事 → 再减少首屏要加载的资源 → 最后才拆 JS。

## 排查顺序

1. Lighthouse：看 LCP / SI / TBT / CLS
2. LCP 差：首屏图片、首屏 API、字体、SSR 等待
3. SI 差：非首屏是否提前加载
4. TBT 差：首屏 JS 与 hydration
5. CLS 差：图片宽高、容器尺寸、动态占位

关键是首屏加载了什么、执行了什么、等了什么——不只是文件大小。

# 示例

首页：首屏只渲染 nav + hero；文章列表与推荐用懒加载 / 延后请求；hero 用 `picture` + 移动端限尺寸；列表图 `loading="lazy"`。

# 总结

不要一上来就拆包。先减首屏负载，再抠图片与移动端尺寸，最后才动 JS / hydration。
