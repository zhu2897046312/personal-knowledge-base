二、 在 Go 后端中的具体实现步骤
以自定义的 CLI 工具（假设叫 mycli）为例，通过 Go 来包装并供大模型调用：
1. 向大模型注册工具（Tool Definition）
在请求大模型时，通过 JSON Schema 告诉大模型这个 CLI 能干什么、接受哪些参数：
{
  "name": "run_my_cli",
  "description": "执行本地 mycli 命令行工具，用于项目部署和测试环境配置",
  "parameters": {
    "type": "object",
    "properties": {
      "subcommand": {
        "type": "string",
        "description": "子命令，例如 deploy, build, status"
      },
      "env": {
        "type": "string",
        "description": "目标环境，例如 dev, test, prod"
      }
    },
    "required": ["subcommand"]
  }
}


2. 后端捕获大模型的调用请求，并调用本地 CLI
当大模型判断需要调用 CLI 时，它不会直接生成文本，而是返回一个 tool_calls 响应。你的 Go 代码解析这个响应并使用 os/exec 执行命令：
package main

import (
	"bytes"
	"fmt"
	"os/exec"
)

// 当大模型触发 Tool Call 时执行此 Go 函数
func ExecuteCLI(subcommand string, env string) (string, error) {
	// 构建真实的系统 CLI 命令：mycli <subcommand> --env=<env>
	args := []string{subcommand}
	if env != "" {
		args = append(args, fmt.Sprintf("--env=%s", env))
	}

	// 1. 创建进程执行 CLI
	cmd := exec.Command("mycli", args...)

	var stdout, stderr bytes.Buffer
	cmd.Stdout = &stdout
	cmd.Stderr = &stderr

	// 2. 运行命令
	err := cmd.Run()
	if err != nil {
		// 如果 CLI 执行报错，将错误标准输出返回给大模型，让它知道错在哪
		return "", fmt.Errorf("CLI 执行失败: %s, 详情: %s", err, stderr.String())
	}

	// 3. 返回 CLI 的标准输出结果
	return stdout.String(), nil
}


3. 将 CLI 结果喂回大模型
将 ExecuteCLI 得到的 stdout 字符串重新打包成一条 role: "tool" 的消息发送给大模型，大模型就会根据 CLI 的真实输出给用户解释执行结果。
三、 生产落地时的安全与工程注意事项
让大模型去跑本地或服务器上的 CLI 工具非常强大，但也存在安全隐患，必须做好防护：
白名单校验与命令隔离（绝对不要传任意命令）
危险做法：允许大模型直接返回一个字符串 sh -c "用户输入的任意命令"，这极易引发任意代码执行（RCE）漏洞。
安全做法：严格限制允许调用的 CLI 命令白名单（如仅允许 mycli），参数使用强类型解析，禁止拼接未经转义的 Shell 字符。
沙盒运行（Sandbox Execution） 如果该 CLI 工具包含文件修改、代码编译或系统运维操作，建议将 CLI 工具打包并限制在 Docker 容器、轻量虚拟机或限制了权限的受控 Linux 用户组内运行，避免操作破坏宿主机环境。
超时与资源限制 CLI 命令执行可能会因为网络超时或死循环卡住。在 Go 中调用时，务必使用 exec.CommandContext 加上 Context 超时控制（例如 context.WithTimeout(ctx, 30*time.Second)），防止系统被阻塞。

三、 落地到实际硬件时，需要注意的 3 个工程细节
如果你想动手做一个小车或桌面智能机器人，需要重点处理以下几个细节：
1. 硬件控制方式：CLI vs 物理串口/GPIO
CLI 方式：在 Linux 系统中，你可以写一个 Go/C++ 编译出的 robot-cli 命令，大模型触发后，后端执行 exec.Command("./robot-cli", "dance")。这种方式最容易开发和调试。
直接控制（GPIO/串口）：如果 Go 服务直接运行在树莓派上，甚至不需要经过 CLI 命令行层，直接在 Go 代码里调用 periph.io 或 gobot 库，操作串口（UART）给单片机（如 ESP32/STM32）发指令，延迟会更低。
2. 工具调用的“防幻觉”与安全断路器（Safety Guard）
大模型在极少数情况下可能会生成越界的参数（比如把速度填成 -999，或者无限循环发送前进命令）。 在 Go 层的工具执行函数里，必须加上安全夹具：
func MoveForward(speed int) error {
    // 强制把速度限制在安全范围内，防止机器人撞墙或电机烧毁
    if speed > 100 { speed = 100 }
    if speed < 0 { speed = 0 }
    
    return exec.Command("./robot-cli", "move", fmt.Sprintf("--speed=%d", speed)).Run()
}


3. 异步动作与中断机制（Interrupt）
如果用户对机器人说：“向前直行 10 秒”，大模型触发了 CLI 命令开始移动；但在第 3 秒时，用户突发喊道：“停下！” 这时候需要你的 Go 后端服务具备打断当前 CLI 进程（Kill Process）的能力，把正在执行的子进程杀掉并立即响应“停止”指令。

2. 在 Go 服务启动时，动态组装 Eino 的 Tool 数组

toolsConfig := adminRepo.GetAllEnabledTools()

var einoTools []eino.Tool

for _, cfg := range toolsConfig {
    // 动态构建 Eino 认识的 Tool 对象
    dynamicTool := eino.NewTool(eino.ToolInfo{
        Name:        cfg.ToolName,
        Description: cfg.Description,
        ParamsSchema: cfg.ParametersSchema, // 直接传入 JSON Schema
    }, func(ctx context.Context, inputJson string) (string, error) {
        
        // 核心逻辑：这里不需要写具体的 if-else，全通用！
        // 1. 将大模型填入的 inputJson 按照模板渲染成硬件 payload
        payload := renderPayload(cfg.ActionConfig.PayloadTemplate, inputJson)
        
        // 2. 将消息推送到 MQTT 或 WebSocket 给本地 ESP32
        mqttClient.Publish(cfg.ActionConfig.MqttTopic, payload)
        
        return "指令已成功下发给硬件设备", nil
    })
    
    einoTools = append(einoTools, dynamicTool)
}

按照这个节奏开发，不仅每一步都有明确的反馈，而且绝不会在 Eino 繁复的抽象概念里迷失。

User prompt: chain链路支持中断吗？ 例如：我说好热开空调，转头就又说，欸，算了我去买个冰镇饮料，你别开了
Response: 不支持，普通的 Chain 链路本身是“无法天然打断并回退状态”的。
因为传统的 Chain 是一条单向同步流（Unidirectional Pipeline）：从请求发起到大模型输出 Tool Calling 参数、再到后端执行你的 CLI / MQTT 控制命令，通常在零点几秒甚至几秒内就串行跑完了。
当你说完“好热开空调”时，后端已经触发了控制指令；你转头说“算了别开了”的时候，其实已经是下一轮独立的 HTTP 请求了。
一、 那这种“中途改变主意”的场景，在工程上是怎么解决的？
针对你说的“说快了、说反了、中途打断”的场景，行业内有两种极具代表性的解法：
方案 1：响应延迟 / 确认队列（最简单、成本最低的 Go 层工程解法）
不靠 LLM 框架的中断，而在 Go 后端的 CLI/MQTT 下发层设计一个“缓冲队列（Buffer Delay）”：
当大模型判断要执行 ac-cli power=on 时，Go 后端不要立刻把指令发给硬件，而是把它放入一个带 3 秒延迟的队列（如 Redis / Go Channel 缓存）。
如果用户在 3 秒内又发了新请求：“算了别开了”，云端大模型识别出 CancelAction 的意图。
Go 后端直接从缓存队列里撤销（Cancel）刚才还没真正发射出去的空调指令，直接响应用户：“好的，已为你取消开空调。”
方案 2：用 Graph 实现“Human-in-the-Loop（挂起与中断）”
如果操作非常高危（比如给客户退款、删除数据库、或者机械臂高危动作），就需要用到 Graph 的 Checkpoint（检查点）与挂起能力：
图节点挂起：Graph 运行到 Execute_CLI 节点前，自动将状态挂起（Pause），并保存当前 State 到数据库。
等待确认或打断：此时系统不往下走，如果用户输入“算了，取消”，条件边直接路由到 Abort 节点，释放状态。
如果用户确认（或倒计时结束），触发 Resume 恢复图的运行，才真正下发硬件指令。
二、 针对智能硬件场景的“打断”最佳实践
在硬件交互中，用户的“打断”通常分为两种不同的物理层意图：

场景类型
用户的真实动作

总结

只有涉及需要长时间运行的复杂 Agent 流程（如：大模型正在帮你跑一个需要 2 分钟的编译脚本，你中途想强行 Pause 并修改参数），才需要用到 Graph 的中断与恢复。

一、 为什么设备多不需要上 Graph？
大模型本身就是一个极强的“路由选择器”。哪怕你注册了 20 个设备的 Tool（空调、冰箱、电脑、洗衣机...），只要每个 Tool 的 description 描述清晰，大模型都能准确找到对应的接口。

二、 如何解决“关机”这种歧义指令？（3 层递进解法）
针对“关机（不知道关哪个）”这种情况，在工程上有三种从简单到智能的解决手段：
1. 第一层：System Prompt 提示词规范（大模型自然反问）
最简单的做法是在 System Prompt 里给大模型下达规则：

交互效果：
用户：“关机。”
大模型（检查发现有多个设备 Tool，意图不明，不触发 Tool）：
回复：“请问您是指关闭空调、风扇还是电脑呢？”
用户：“电脑。”
大模型（结合上一轮对话上下文）：
触发 Tool：pc_power_off()
这一步只需要标准的 Chain + 多轮 History 存储就能自然跑通，零额外开发成本。
2. 第二层：结合“当前设备运行状态”（智能推断，减少废话）
很多时候用户说“关机”，是因为他心里觉得“反正现在就开着这一个设备”。

}

场景 A（只有一个设备开着）：

用户：“关机。”

Go 服务拦截到这个 Tool Call，发现它是高危动作。

User prompt: api调用输出的json，怎么清洗成mqtt需要的json？
Response: 将大模型 API 输出的 JSON（意图抽取结果）清洗/转换成 MQTT 需要的 JSON（硬件控制指令），本质上是一个数据映射与格式化（Data Mapping & Transformation）的过程。
在实际工程中，最常用且扩展性最好的实现方式有以下 3 种方案：
方案一： Go text/template 模板引擎（推荐：适合 Admin 动态配置）
为了实现之前讨论的“不改 Go 代码、Admin 后台配置新硬件”，最优雅的方式是把 MQTT JSON 结构写成模板 存入数据库，Go 服务用标准库 text/template 动态渲染。
1. 数据流过程示例
大模型 API 输出（LLM Output）：
{
  "power": "on",
  "temperature": 26,
  "fan_speed": "high"
}


Admin 预设的 MQTT 渲染模板（Stored Template）：
{
  "device": "living_room_ac",
  "cmd": 101,
  "pwr": {{if eq .power "on"}}1{{else}}0{{end}},
  "temp": {{.temperature}},
  "spd": {{if eq .fan_speed "high"}}3{{else if eq .fan_speed "medium"}}2{{else}}1{{end}}
}


最终清洗输出的 MQTT JSON：
{
  "device": "living_room_ac",
  "cmd": 101,
  "pwr": 1,
  "temp": 26,
  "spd": 3
}


2. Go 核心清洗代码实现
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"text/template"
)

// CleanLLMToMQTT 将 LLM 的 JSON 字符串根据模板清洗为 MQTT JSON
func CleanLLMToMQTT(llmJson string, tplStr string) (string, error) {
	// 1. 将 LLM 输出解析为通用 Map
	var data map[string]any
	if err := json.Unmarshal([]byte(llmJson), &data); err != nil {
		return "", fmt.Errorf("解析大模型 JSON 失败: %v", err)
	}

	// 2. 解析 Go 模板
	tmpl, err := template.New("mqtt").Parse(tplStr)
	if err != nil {
		return "", fmt.Errorf("解析 MQTT 模板失败: %v", err)
	}

	// 3. 渲染模板
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, data); err != nil {
		return "", fmt.Errorf("渲染 MQTT 指令失败: %v", err)
	}

	// 4. 二次校验：确保生成的最终结果是合法的 JSON
	var validateCheck map[string]any
	if err := json.Unmarshal(buf.Bytes(), &validateCheck); err != nil {
		return "", fmt.Errorf("生成的 MQTT 指令不是有效 JSON: %v", err)
	}

	return buf.String(), nil
}


方案二： Struct 强类型映射（适合固定设备、追求极致性能）
如果你对某几个特定设备的控制格式非常固定，追求极致的执行效率，可以使用 Go 的 Struct 强类型反序列化与转换。
// 1. 大模型返回的数据结构
type LLMACInput struct {
	Power       string `json:"power"`
	Temperature int    `json:"temperature"`
	FanSpeed    string `json:"fan_speed"`
}

// 2. ESP32 要求的 MQTT 数据结构
type MQTTAcPayload struct {
	Cmd  string `json:"cmd"`
	Pwr  int    `json:"pwr"`
	Temp int    `json:"temp"`
	Spd  int    `json:"spd"`
}

// 3. 清洗映射函数
func TransformACToMQTT(llmJson string) ([]byte, error) {
	var in LLMACInput
	if err := json.Unmarshal([]byte(llmJson), &in); err != nil {
		return nil, err
	}

	// 编写清洗与转换逻辑
	out := MQTTAcPayload{
		Cmd:  "AC_CTRL",
		Temp: in.Temperature,
		Pwr:  0,
		Spd:  1,
	}

	// 枚举值清洗转换 (Value Normalization)
	if in.Power == "on" {
		out.Pwr = 1
	}

	switch in.FanSpeed {
	case "high":
		out.Spd = 3
	case "medium":
		out.Spd = 2
	case "low":
		out.Spd = 1
	}

	return json.Marshal(out)
}


方案三： 通用映射字典 + JSON 路径提取（JSON-to-JSON Mapper）
如果有些硬件只需要改变 字段 key 的名称（例如 LLM 输出 temperature，ESP32 只需要 t），可以采用字典映射库（如 tidwall/gjson + tidwall/sjson）。
package main

import (
	"github.com/tidwall/gjson"
	"github.com/tidwall/sjson"
)

// MappingRule: LLM字段路径 -> MQTT字段路径
var acMapping = map[string]string{
	"temperature": "params.t",
	"power":       "params.p",
}

func QuickTransform(llmJson string) string {
	mqttJson := "{}"

	for llmKey, mqttPath := range acMapping {
		// 提取 LLM JSON 中的字段值
		val := gjson.Get(llmJson, llmKey)
		if val.Exists() {
			// 设置到 MQTT JSON 目标路径中
			mqttJson, _ = sjson.Set(mqttJson, mqttPath, val.Value())
		}
	}

	return mqttJson
}


关键数据清洗与防护细节（边界防错）
在大模型清洗为 MQTT 指令时，必须做好以下 3 个防护措施：
数值范围裁剪（Boundary Clamping）
问题：大模型可能误返回 temperature: 99。
处理：在清洗逻辑或模板中做限制：if temp > 30 { temp = 30 }。
默认值兜底（Fallback Values）
问题：大模型可能遗漏非必填字段（如只传了 power: "on"，没传 temperature）。
处理：清洗逻辑中发现字段缺失时，赋予安全的默认值（如默认 26 度）。
类型强制转换（Type Cast）
问题：大模型可能将数字返回为字符串（例如 "temperature": "26"）。
处理：在转换层使用 strconv.Atoi() 或 Go 模板的强转能力，确保 MQTT 发给 ESP32 的是 int 类型数字而非字符串。
选型建议
做 Admin 配置化 / 零代码加设备 → 用 方案一（text/template），最通用灵活。
做 核心固定设备 / 追求高吞吐量 → 用 方案二（Struct 强类型转换）。

func HandleLLMToolCall(llmJson string, deviceID string) ([]byte, error) {
	// 1. 强类型解析：校验大模型返回的数据格式
	var cmd device.DeviceCommand
	if err := json.Unmarshal([]byte(llmJson), &cmd); err != nil {
		return nil, fmt.Errorf("大模型输出格式非法: %v", err)
	}
	cmd.DeviceID = deviceID

	// 2. 强类型校验：在 Go 层做业务兜底，防止坏数据下发到硬件
	if cmd.Value != nil && (*cmd.Value < 16 || *cmd.Value > 30) {
		// 自动矫正超出范围的数值
		clampedVal := math.Max(16, math.Min(30, *cmd.Value))
		cmd.Value = &clampedVal
	}

	// 3. 从数据库/缓存获取 Admin 配置的模板
	config := adminRepo.GetDeviceConfig(deviceID)

	// 4. 将强类型的 Struct 直接喂给模板渲染
	tmpl, _ := template.New("mqtt").Parse(config.PayloadTemplate)
	var buf bytes.Buffer
	if err := tmpl.Execute(&buf, cmd); err != nil {
		return nil, fmt.Errorf("MQTT 渲染失败: %v", err)
	}

	return buf.Bytes(), nil
}

一、 核心解法：如何区分“命令”与“杂音/闲聊”？
1. 语义意图阈值与 Tool 匹配（最核心的过滤网）

规则：

2. 声纹识别与声源定位（定向过滤）
纯靠文字容易出现误触发（比如你看电视，电视里正好喊了一句“把灯关了”）。
声场定位（Microphone Array Beamforming）：利用多麦克风阵列计算声音到达的时差。如果声音来自电视机方向，直接过滤；如果声音来自房间中央的人，才进行响应。
声纹锁（Voiceprint Matching）：只识别并响应绑定了的主人（如你的声音），电视机里的说话声或路人的声音直接忽略。
3. 视听融合（Visual-Language Model / 眼神注意力）
这是目前高端智能硬件（如苹果 Vision Pro、带摄像头的桌面机器人）最倾向的方案：不仅用耳朵听，还用眼睛看。

如果你看着它说：“开一下空调” → 执行。
如果你看向旁边的人说：“开一下空调” → 判定为人类之间的对话，忽略。
4. 本地端侧轻量小模型前置过滤（VAD + VLM）

第一关（VAD 语音活动检测）：ESP32 或树莓派本地跑 VAD，过滤掉电视杂音、关门声、风声，只在有人说话时才录音。

1. 简易实现逻辑（Python 示例）

import json
import subprocess
import paho.mqtt.client as mqtt

# 1. 收到 MQTT 消息时的回调
def on_message(client, userdata, msg):
    try:
        data = json.loads(msg.payload.decode('utf-8'))
        print(f"收到控制指令: {data}")

        # 解析指令
        power = data.get("power", "OFF")
        temp = data.get("temp", 26)
        mode = data.get("mode", "COOL")

        # 2. 调用本地红外工具 (如 ir-ctl 或 lirc) 发送指令
        # 很多开源库（如 Python 的 pyirsend 或调用系统的 ir-ctl）支持直接发送空调编码
        cmd = f"ir-ctl -S gree:POWER_{power}_TEMP_{temp}_{mode}"
        subprocess.run(cmd, shell=True)
        print("红外信号已发射！")

    except Exception as e:
        print(f"解析或发射失败: {e}")

# 2. 连接 MQTT Broker
client = mqtt.Client()
client.on_message = on_message
client.connect("192.168.1.X", 1883, 60) # 替换为你的 MQTT Broker IP
client.subscribe("home/livingroom/ac/command")

print("本地控制器已启动，等待 MQTT 指令...")
client.loop_forever()

2. Go 发送 MQTT 指令代码
package main

import (
	"encoding/json"
	"fmt"
	"log"
	"time"

	mqtt "github.com/eclipse/paho.mqtt.golang"
)

// ACCommand 空调控制结构体
type ACCommand struct {
	Power string `json:"power"` // ON / OFF
	Mode  string `json:"mode"`  // COOL / HEAT
	Temp  int    `json:"temp"`  // 16-30
	Fan   string `json:"fan"`   // AUTO / LOW / MED / HIGH
}

func main() {
	// 1. MQTT 连接配置
	opts := mqtt.NewClientOptions()
	opts.AddBroker("tcp://192.168.1.X:1883") // 替换为你的 MQTT Broker 地址
	opts.SetClientID("go_backend_server")

	client := mqtt.NewClient(opts)
	if token := client.Connect(); token.Wait() && token.Error() != nil {
		log.Fatalf("MQTT 连接失败: %v", token.Error())
	}
	defer client.Disconnect(250)

	// 2. 构造开空调指令（开启、制冷、26度）
	cmd := ACCommand{
		Power: "ON",
		Mode:  "COOL",
		Temp:  26,
		Fan:   "AUTO",
	}

	payload, err := json.Marshal(cmd)
	if err != nil {
		log.Fatalf("JSON 序列化失败: %v", err)
	}

	// 3. 发布消息到 MQTT Topic
	topic := "home/livingroom/ac/command"
	token := client.Publish(topic, 0, false, payload)
	token.Wait()

	fmt.Printf("成功下发 MQTT 控制指令到 [%s]: %s\n", topic, string(payload))
}
